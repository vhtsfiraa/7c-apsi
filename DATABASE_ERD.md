# Job Laundry database

The Prisma schema and `database_job_laundry.sql` describe the six business
tables in the final ERD. PostgreSQL table and column names are quoted and
case-sensitive to match the ERD exactly.

## Tables and keys

| Table | Primary key | Foreign keys and purpose |
|---|---|---|
| `MEMBER` | `ID_Member` | Member name, optional phone and gender, registration date |
| `PEGAWAI` | `ID_Pegawai` | Cashier and optional supervisor identities |
| `TRANSAKSI` | `Kode_Transaksi` | References one member and one cashier; optional supervisor; stores weight, clothing notes, pricing and coin/notifier values |
| `STATUS` | `ID_Status` | Laundry status master data |
| `STATUS_PROSES` | (`Kode_Transaksi`, `ID_Status`) | References a transaction and status; records the time each status is reached |
| `USERS` | `ID_User` | Unique username and password hash; each login account references a staff member |

`TRANSAKSI.ID_Kasir` and `TRANSAKSI.ID_Supervisor` are separate relations to
`PEGAWAI`. A Member has many transactions. Transactions have many status
process rows, and each status can be used by many process rows.

IDs are generated by the application before insert. Phone number is nullable
because the legacy database contains one Member without a phone number; new
registrations require it. The ERD does not define a unique constraint for
`No_HP`.

## Authentication

Cashier credentials are stored in `USERS`; their session identity is the
referenced `PEGAWAI.ID_Pegawai`. The demo cashier username is `kasir`, with
password `kasir` hashed using the application's scrypt format.

There is no Member-to-`USERS` relation in this ERD. Member login therefore
uses `ID_Member` and `No_HP`; registration continues to ask only for a name and
phone number. Member password accounts from the old schema are not copied to
the new ERD tables.

## Feature mapping and ERD limits

- Current status and status history use `STATUS_PROSES`; the composite key
  means a transaction can record a given status only once.
- Coin balances are calculated from transaction `Koin_Didapat` minus
  `Koin_Ditukar`. Manual adjustments are represented by zero-weight
  transactions with explanatory clothing notes.
- Completion notification time is stored in
  `TRANSAKSI.Waktu_Notifikasi_Selesai`.
- A pickup request is represented as a `Menunggu Pengambilan` status process;
  final handoff is `Sudah Diambil`.
- The ERD has no notification read-state or independent pickup-request fields.
  Those details cannot be persisted without changing the ERD.

## Migration and SQL

The migration `prisma/migrations/20261110000000_legacy_baseline` marks the
pre-existing schema as a baseline without running DDL. The next migration
creates the six ERD tables and copies compatible Member, staff, transaction,
status, notification-time, pickup-status and standalone coin-history data.
A follow-up migration reconciles any remaining legacy Member coin balances
using transaction coin fields.
It does not drop or rename the old lowercase tables. In particular,
`public.users` remains in place as a legacy source table while the new quoted
`"USERS"` is used by the ERD.

The database migration was run with `prisma migrate deploy` against the
configured PostgreSQL database and is additive. Review and back up the legacy
tables before any later cleanup; cleanup is not included in these migrations.

`database_job_laundry.sql` is a standalone PostgreSQL script for `psql`; it
creates/connects to `job_laundry`, creates the six tables, and seeds status
master rows and the demo cashier. It is not the migration for an existing
database.
